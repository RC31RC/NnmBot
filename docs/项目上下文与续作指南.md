# NnmBot 项目上下文与续作指南

更新时间：2026-10-08

本文是新开发会话的项目入口。它说明当前项目做什么、各仓库如何配合、参考项目在哪里、
Warframe 数据如何进入系统，以及当前配置和数据表的边界。它不是替代
[`AGENTS.md`](../AGENTS.md) 的开发规范；开始修改代码前仍应先阅读 `AGENTS.md`。

## 1. 项目是什么

NnmBot 是一个 Java 21、Spring Boot 4、多模块 Maven 的 Warframe QQ 机器人后端，
同时提供管理端 API。当前主要工作是把 Warframe 的官方目录、官方动态 WorldState、
Warframe Market 和多个社区静态 JSON 来源整理成可追溯、可刷新、可人工审核的数据链路。

项目包含两类运行数据：

- **官方/外部运行数据**：官方 WorldState、Warframe Market API、论坛和其他实时接口；
- **可审计静态数据**：官方 Public Export 入库数据，以及社区 JSON 刷新后经管理端预览、
  勾选、合并的数据。

参考项目只用于离线阅读、字段核对、规则复核和来源追溯，不是 NnmBot 的运行时依赖。
不能因为本机存在某个参考项目，就在业务代码中直接读取其本地文件。

## 3. 模块边界

```text
nnm-app
  -> nnm-admin
  -> nnm-warframe
  -> nnm-core
  -> nnm-render

nnm-admin  -> nnm-core -> nnm-common
nnm-warframe -> nnm-core / nnm-render / nnm-common
nnm-render -> nnm-core / nnm-common
```

- `nnm-common`：错误、响应、HTTP、校验和无业务域基础设施。
- `nnm-core`：OneBot、QQ 官方机器人、消息、命令执行、群组、JMComic 和后台任务。
- `nnm-render`：HTML、图片、PDF 和受控渲染扩展。
- `nnm-warframe`：Warframe 客户端、解析器、实体、社区数据、WorldState、Market 和命令。
- `nnm-admin`：`/api/admin/v1`、Sa-Token、RBAC、机器人配置和管理业务。
- `nnm-app`：Spring Boot 组装、YAML 配置和集成测试。

数据库结构由 `docs/sql/init.sql` 和根目录下的手工修复脚本维护，Hibernate 只做
`validate`。业务表使用 PostgreSQL 的 `nnmbot` schema。缓存和分布式任务使用 Redis；
JVM 业务缓存使用 cache2k。

## 4. Warframe 数据边界

### 4.1 官方 Public Export

官方 Public Export 是官方目录数据，不属于社区数据表。主要落入：

- `wf_official_export_record`：官方原始/结构化导出记录；
- `wf_official_weapon`、`wf_official_warframe`：武器和 Warframe 投影；
- `wf_official_upgrade`：Mod、升级和相关官方字段；
- `wf_official_relic_arcane`：官方遗物/奥金相关目录；
- `wf_official_region`：官方 `ExportRegions` 节点和星图结构；
- `wf_official_recipe`：官方配方。

官方本地化字段和社区 `dict.zh.json`/`dict.en.json` 是两条不同链路。运行时名称解析可以
使用官方字段和社区字典，但不能把官方表和社区翻译表误合并成一张表。

### 4.2 官方 WorldState

`worldState.php` 是实时动态快照，主要保留在 JVM WorldState 模型和 cache2k 中，
不把每次动态快照作为社区静态数据入库。静态代码簿可以从
`warframe-worldstate-data/data/zh/*.json` 刷新到对应的 `wf_community_worldstate_*`
表，用来解释动态快照中的代码。

### 4.3 Warframe Market

Market 商品、订单和拍卖优先通过 Warframe Market API 获取并使用 cache2k 缓存。
Market 社区 JSON 只用于已登记的静态目录、紫卡词条或辅助规则，不代替实时订单接口。

## 5. 社区数据配置模型

当前统一配置位于：

`nnm-app/src/main/resources/application-bot.yml`

绑定类位于：

`nnm-warframe/src/main/java/com/nnm/bot/warframe/config/properties/WarframeCommunityDataProperties.java`

配置结构统一为：

```yaml
nnm:
  warframe:
    community-data:
      datasets:
        translation:
          - source-code: warframe-public-export-plus:dict.zh.json
            urls:
              - https://example.test/dict.zh.json
              - https://mirror.test/dict.zh.json
        map_feature:
          - source-code: warframe-hub:data/json/geo/vallis/labels.json
            url: https://example.test/labels.json
            world: vallis
```

含义如下：

- `datasets` 是数据集到来源列表的唯一配置入口；
- 列表只有一项，表示单来源数据集；
- 列表有多项，表示同一业务数据集的多个来源；
- `source-code` 是数据库审计、来源隔离和删除比对的稳定身份；
- `url` 是一个来源的单个地址；
- `urls` 是同一个来源的候选/故障转移地址，不表示多个业务来源；
- `world` 是解析 `map_feature` 时写入记录的地图所属开放世界分类；
- `world` 不是数据库地址、Redis 地址、HTTP 代理或连接配置。

因此，旧的 `dataset-urls` 和 `dataset-manifests` 不再表达两种不同的数据模型，也不应
重新添加。当前代码使用 `getDatasets()`，Java 内部类型为 `DatasetSource`。

### 6.3 节点来源结论

管理端“社区数据 -> 节点”当前只显示：

`kingprimes:warframe/nodes.json`

这是当前设计的正确行为，不代表来源缺失。节点相关资料实际上按职责分为三类：

## 7. 刷新、Redis 和数据库写入

普通社区刷新流程是：

```text
获取数据集锁
  -> SourceLoader 并行下载、解析 datasets 中的登记来源
  -> 每个来源由 Client 按配置顺序尝试 CDN
  -> 成功来源按 source-code 独立比对数据库 COMMUNITY 记录
  -> 生成新增/修改/删除预览和失败来源摘要
  -> PreviewStore 保存 Redis 预览分片
  -> 管理端按来源、变更类型选择
  -> 事务写入 PostgreSQL
```

自维护记录属于 `SELF_MAINTAINED`，不能被社区来源刷新覆盖或删除。单个来源下载或解析失败时，
保留该来源原数据，不生成新增、修改或删除操作；成功来源继续生成 diff。失败不能当成空数组，
合法且解析成功的空数据才允许生成该来源的删除候选。全部来源失败仍返回可查看的失败摘要预览，
但不建立待确认索引，因此不阻塞下一次刷新。

来源下载和纯解析使用 `ExecutorConfig` 的独立有界 `communitySourceExecutor`，默认并发 2、
队列 8，配置为 `nnm.executor.community-source-concurrency` 和
`nnm.executor.community-source-queue-capacity`。父刷新任务不占用此池，来源线程不访问数据库；
数据库比对和预览发布仍在协调线程执行，避免放大默认 5 个数据库连接的占用。队列满时调用方承担
工作形成背压；协调线程统一更新进度，普通等待期间每 5 秒报告心跳。来源结果按配置顺序返回，
不会因为并行完成顺序改变中英文和来源分组。

### 7.1 Redis 预览与序列化

`cache/WarframeCommunityPreviewStore` 统一管理 Redis key、分片、压缩、旧格式兼容、分页范围读取、
分组索引和消费清理。`WarframeCommunityDatasetServiceImpl` 保留来源比对、业务分组、数据库基线
校验和提交后消费时机；不把业务规则迁入缓存组件或 `nnm-common`。

预览由记录分片、差异分片和轻量 header 组成。记录/差异分片按 RDT 实际 JSON 的 UTF-8
字节数划分，每片最多 256 KiB，计算包括数组括号、逗号和字符串转义；超限单条记录在任何
Redis 写入前被拒绝。不能把完整预览重新作为几十 MB 的单个 `PSETEX` 值写入 Redis。
分片计算只逐条计量，不反复序列化正在增长的整块列表。

记录快照省略与 `upstreamJson` 相同的 `currentJson`，以及默认 `{}` 的
`manualFieldsJson`，读取分片时恢复完整字段；旧版完整字段分片仍可读取。
`originalJson` 保留，采纳时仍用它校验预览生成后数据库是否被并发修改。此优化减少重复
JSON 和空字段，不改变分页响应、人工覆盖或合并语义。

记录和差异分片序列化后会尝试使用 GZIP，再以带 `gzip1:` 版本前缀的 Base64 字符串交给
RDT 保存；只有压缩结果连同 RDT 的 JSON 字符串引号仍小于原 JSON 时才压缩，避免短数据
反而膨胀。读取同时兼容旧的对象分片、未压缩 JSON 字符串和当前压缩格式。后续若更换压缩
算法，应增加新的版本前缀并保留旧前缀读取能力。

分组索引也单独保存为 `warframe-community-preview-group:{previewId}`，使用相同的压缩协议；
header 只保留分片数量和大小，不再重复保存全部 operation ID。读取时优先兼容旧 header
内嵌索引，找不到时读取独立索引，旧快照仍可回退完整组装。
普通分页利用分片大小索引只读取当前页相交的记录分片；来源和变更类型筛选使用 operation ID
到记录位置的索引，只读取当前分组当前页命中的记录分片，不加载全部差异分片。正式合并仍组装并
校验完整快照。遗物子表预览与缺少分页索引的旧批次保留完整组装回退。

项目业务映射器是 Jackson 2（`com.fasterxml.jackson`），RDT 编解码器是 Jackson 3
（`tools.jackson`）。不要把 Jackson 2 `JavaType` 传入 `CacheService.get`：
它不是 Jackson 3 的集合类型，会触发 `Unrecognized Type`。当前通过 `Object.class`
读取 header/分片；已是目标对象时直接使用，Map 则由业务映射器逐条转换。

### 7.2 原子性边界

- 先写全部记录、差异分片和分组索引，最后写 header 作为发布标记，再写待确认索引。
- 分页校验当页读取的分片，正式合并校验全部声明分片；分片缺失或格式错误会拒绝相应读取或采纳。
- 写入失败补偿清理计划中的全部分片、分组索引、header 和待确认索引；各键独立尽力清理，
  单个删除失败不阻止其余步骤。Redis 不可用导致清理失败时，
  残留键依靠 TTL 过期。RDT 可能已成功写值、但发送失效通知失败，因此不能只清理确认成功的键。
- 采纳时，PostgreSQL 业务变更和 `WarframeCommunityMergeReceipt` 在同一事务提交；
  事务回滚保留预览供重试。提交后才消费/清理 Redis，即使清理失败也由数据库回执阻止重放。

这是发布标记、完整性检查和失败补偿，不是 Redis 多键事务，也不是 Redis 与 PostgreSQL
的跨系统事务。真实测试服连接稳定性、多实例长事务和锁租约失效仍需环境验收。

### 7.3 仲裁与官方导入

仲裁排期从管理端“Warframe 社区数据 -> 仲裁排期”刷新和查看，使用
`arbitration_schedule` 的普通 query/refresh/preview/merge 接口。预览同样按来源和
新增/修改/删除分组、分页并支持跨页全选。排期主键仍为 activation，新增候选使用 RDT
操作 ID，已有候选使用 activation 字符串；无需修改排期表为普通社区记录表。
它是可刷新但禁止人工 CRUD 的只读数据集（`refreshable=true`、`manageable=false`、
`readOnly=true`）：允许采纳上游新增、修改和删除，不允许人工新增、上传、修改或删除。
后端拒绝所有人工入口，前端按 `manageable && !readOnly` 控制入口。统一批量刷新包含已配置的
仲裁排期，没有独立定时任务绕过预览直接写库。
删除候选只在本次上游覆盖的时间窗口内产生，窗口外历史和未来记录不会被当作上游删除。
旧 `/warframe/arbitration/*` 接口保留兼容，不再作为管理端主入口；两种预览 ID 不混用。

官方 Public Export 入库使用批量处理，避免逐条查询、逐条 flush 导致入库时间异常增长。

### 7.4 管理端任务通知

- 刷新按钮仅在提交请求时显示加载动画；再次点击由后端复用当前用户同类型的活动任务。
- 同一任务在前端共享 SSE 订阅，并独立查询任务状态，避免长连接漏掉终态导致一直等待。
  终态会关闭连接和清理轮询，临时查询失败允许重试。
- 社区单数据集和批量刷新完成后，通知提供“审核”入口；从其他页面点击也会回到社区
  数据页面打开已有预览或批量结果，不强制自动弹窗。通知目前只保留在当前页面会话内。
- 响应写出期间的 `Broken pipe` 表示客户端连接已断开，按断连处理；真正的序列化错误
  仍保留错误日志和统一错误响应。

字典记录的最低完整性要求是 `recordKey`、`locale`（`zh`/`en`）和非空
`displayName`。中文和英文必须分别保留，不能只按 `recordKey` 覆盖。
