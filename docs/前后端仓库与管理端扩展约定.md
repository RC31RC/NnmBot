# NnmBot 前后端仓库与管理端扩展约定

> 文档日期：2026-07-24  
> 后端仓库：`/Users/ren/RcGit/NnmBot`  
> 前端仓库：`/Users/ren/RcGit/nnm-admin-web`

## 1. 结论

NnmBot 采用前后端分离、同级独立仓库的组织方式：

```text
/Users/ren/RcGit/
├── NnmBot/             Java 后端、Bot 运行时和管理 API
└── nnm-admin-web/      Vue 管理端
```

`nnm-admin-web` 来源于 Art Design Pro，但已经移除原项目的 Git 元数据，并初始化为新的独立仓库。后续修改不再提交到原 `art-design-pro` 仓库；原项目的 `LICENSE` 和源码署名继续保留。

选择独立仓库的原因：

- Java 与 Node.js 使用不同的构建、测试和发布流程；
- 管理端可以独立部署，也可以由网关或 Nginx 与后端组合发布；
- Bot 后端不依赖前端构建产物，单机运行时可以不部署管理端；
- 未来增加用户端、移动端或文档站时，不需要调整后端仓库结构；
- 前后端通过版本化 API 契约协作，不通过共享源码形成耦合。

## 2. 当前前端适用性

`nnm-admin-web` 当前技术栈包括 Vue 3、TypeScript、Vite、Element Plus、Pinia、Vue Router 和 Axios，能够作为 NnmBot 管理端基础架子。

已有权限能力：

- 登录状态、Access Token 和 Refresh Token 数据结构；
- 前端静态菜单与后端动态菜单两种模式；
- 动态路由注册和未授权路由拦截；
- `meta.roles` 页面角色过滤；
- `v-roles` 角色级组件控制；
- `v-auth` 和 `authList` 按钮权限控制；
- 用户、角色、菜单管理页面骨架。

这些能力可以复用，但前端权限只能用于界面展示和操作引导，不能作为安全边界。所有管理 API 必须由后端再次校验身份和权限。

## 3. 仓库职责

### 3.1 NnmBot 后端

后端负责：

- 管理员认证、Token 签发、刷新和失效；
- 用户、角色、权限、菜单的数据模型；
- API 级权限校验；
- Bot 实例、群组、订阅、任务和数据源管理；
- 操作审计、任务记录和敏感字段脱敏；
- OpenAPI 文档与稳定的接口契约；
- 世界状态、市场、遗物、紫卡等实际业务能力。

`nnm-admin` 是管理 API 的入口，不应承载 Warframe 领域实现。它通过应用服务调用 `nnm-core`、`nnm-warframe`、`nnm-scheduler` 等模块。

### 3.2 nnm-admin-web 前端

前端负责：

- 登录、会话续期和退出；
- 菜单、路由和页面状态；
- 表格、表单、图表及管理工作流；
- 根据后端返回的角色和权限点隐藏不可用操作；
- API 请求适配、错误提示和表单校验；
- 独立构建、静态资源发布和反向代理配置。

前端不得自行判定用户是否真正有权执行敏感操作，也不得保存数据库密码、Sa-Token 服务端密钥、Bot Token 等服务端密钥。

## 4. RBAC 设计约定

### 4.1 权限模型

当前采用标准关系：

```text
sys_user
  -> sys_user_role
  -> sys_role
  -> sys_role_permission
  -> sys_permission
```

菜单不是权限本身。菜单用于导航，权限点用于保护 API 和操作。一个页面可以关联多个权限点，例如：

```text
system:user:view
system:user:create
system:user:update
system:user:disable
system:role:assign
bot:instance:restart
warframe:data:refresh
notification:rule:update
```

前端的 `authMark` 应直接使用上述稳定权限编码，不使用 `add`、`edit` 这类缺少业务域的短名称。

### 4.2 默认角色

第一阶段提供三个内置角色：

| 角色 | 用途 |
| --- | --- |
| `R_SUPER` | 全部权限、角色授权和系统级配置 |
| `R_ADMIN` | 用户管理等日常管理能力 |
| `R_USER` | 只读能力预留，随业务菜单逐步配置 |

内置角色可以扩展，但权限编码一旦发布应保持稳定。角色名称可以调整，API 权限点不应随页面文案变化。

### 4.3 校验顺序

请求处理顺序固定为：

```text
Sa-Token 身份认证
  -> 账户状态检查
  -> API 权限校验
  -> 参数校验
  -> 业务操作
  -> 审计记录
```

前端的路由守卫、`v-roles` 和 `v-auth` 只做体验优化。即使用户绕过前端直接调用 API，后端也必须返回 `401` 或 `403`。

## 5. API 契约

### 5.1 基础约定

- 管理 API 统一使用 `/api/admin/v1` 前缀；
- 健康检查和 Actuator 可使用独立路径；
- Token 使用 `Authorization: Bearer <token>`；
- 时间统一返回 ISO 8601，并带明确时区；
- 当前管理端分页参数统一为 `current`、`size`；
- 当前列表响应统一包含 `records`、`current`、`size`、`total`；
- 新增破坏性变更时发布 `/v2`，不直接修改已发布语义。

统一响应结构以后端现有 `ApiResponse` 为准：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

前端模板原先使用 `msg` 字段，需要适配为 `message`。

### 5.2 RBAC 已完成接口

当前第一阶段接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/admin/v1/auth/login` | 登录并返回 Token |
| `POST` | `/api/admin/v1/auth/refresh` | 刷新 Token |
| `POST` | `/api/admin/v1/auth/logout` | 当前会话退出 |
| `GET` | `/api/admin/v1/me` | 当前用户、角色和权限点 |
| `GET` | `/api/admin/v1/menus` | 当前用户可见菜单 |
| `GET/POST` | `/api/admin/v1/users` | 用户分页和创建 |
| `PUT` | `/api/admin/v1/users/{userId}` | 修改用户和角色 |
| `PUT` | `/api/admin/v1/users/{userId}/status` | 启用或禁用用户 |
| `GET/POST` | `/api/admin/v1/roles` | 角色分页和创建 |
| `PUT/DELETE` | `/api/admin/v1/roles/{roleId}` | 修改或删除角色 |
| `GET/PUT` | `/api/admin/v1/roles/{roleId}/grants` | 查询或保存角色授权 |
| `GET` | `/api/admin/v1/permissions` | 权限点列表 |
| `GET` | `/api/admin/v1/menus/all` | 完整菜单管理树 |
| `POST/PUT/DELETE` | `/api/admin/v1/menus`、`/menus/{menuId}` | 菜单管理 |
| `POST/PUT/DELETE` | `/api/admin/v1/permissions`、`/permissions/{permissionId}` | 按钮权限管理 |
| `GET` | `/api/admin/v1/operation-logs` | 操作审计 |
| `GET/DELETE` | `/api/admin/v1/sessions`、`/sessions/{token}` | 在线会话和强制下线 |

后端菜单接口只返回前端已注册的组件标识，不返回任意文件路径。前端维护“组件标识到 Vue 页面”的白名单映射，避免动态加载任意模块。

角色数据范围支持 `ALL` 和 `SELF`。当前先用于用户列表查询，新增业务资源时
由对应 Service 按资源归属实施过滤。Sa-Token 当前使用默认内存 DAO，单机
运行足够；多实例部署前必须切换为 Redis 等共享会话存储。

## 7. 前端扩展边界

前端建议逐步收敛为以下结构：

```text
src/
├── api/                 按后端业务域组织 API
├── features/            可独立演进的业务功能
│   ├── auth/
│   ├── dashboard/
│   ├── bot/
│   ├── warframe/
│   ├── notification/
│   ├── scheduler/
│   └── system/
├── components/          无业务依赖的公共组件
├── router/              路由注册、菜单转换和守卫
├── store/               全局会话和跨页面状态
├── types/               API 与公共类型
└── utils/               无业务语义的工具
```

不要求立即重构模板目录。新增业务页面应优先进入对应业务域，确认至少出现两处真实复用后再抽取公共组件。

后续如果出现多个前端，可以演进为：

```text
nnm-admin-web       管理端
nnm-user-web        用户查询与订阅端
nnm-docs            文档站
```

只有在多个前端确实需要共享 API 类型、设计令牌或组件时，再建立 `nnm-web-shared` 包或前端 monorepo。当前阶段不提前增加该复杂度。

## 8. 部署与本地开发

本地开发：

```text
nnm-admin-web : http://localhost:3006
NnmBot API    : http://localhost:8080
```

Vite 将 `/api` 代理到后端，浏览器只访问前端开发服务器。生产环境推荐同域部署：

```text
https://nnm.example.com/          前端静态资源
https://nnm.example.com/api/      反向代理到 NnmBot
```

同域部署可以减少 CORS、Cookie 和环境地址管理成本。如果以后独立域名部署，再由后端配置明确的 CORS 白名单，禁止使用通配来源配合凭证。

## 9. 演进原则

1. 单机阶段保持模块化单体，不为了可能的多实例提前引入微服务。
2. 前后端独立发布，但 API 契约必须版本化并有测试。
3. RBAC 以后端为唯一安全边界。
4. 菜单与权限点解耦，页面改名不影响 API 权限编码。
5. 新功能按业务域扩展，不在 `common` 或全局 store 中堆积业务逻辑。
6. 外部 API、Bot 平台、渲染引擎和消息发送器继续通过接口隔离。
7. 当出现第二个真实实现或明确替换需求时再抽象，不为抽象本身增加层次。
8. 前端仓库保留原 MIT 许可和来源说明；NnmBot 自有业务代码按项目最终选择的开源许可发布。
