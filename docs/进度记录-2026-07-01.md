## 二、关键技术决策（备查）

### 容错选型：OpenFeign / Dubbo vs resilience4j / Sentinel
- 它们是**不同层面**：OpenFeign/Dubbo 负责"发起调用"，resilience4j/Sentinel 负责"调用兜底"，叠加而非替代。
- 超时（单次最多等多久）、重试（失败再试）、Sentinel（基于统计的熔断限流）三者并存，引入后都保留。
- **NnmBot**（个人 Bot，失败影响小）→ 只要超时 + 幂等 GET 重试，不要熔断。
- **charge-operator**（生产级充电交易微服务）→ 用 **Sentinel**（与已有 Dubbo+Nacos 同属阿里系，整合最顺、可接 Nacos 动态规则、有 Dashboard），而非 resilience4j。

### 渲染依赖选型（4G 内存约束）
- openhtmltopdf 是 xhtmlrenderer(Flying Saucer，NyxBot 在用) 的现代化 fork，CSS3 支持更好、同样省内存 → 纯 Java 渲染里 openhtmltopdf 更优。
- 但纯 Java 渲染都做不到 Playwright（真 Chromium）的完整阴影/渐变。
- 4G 服务器跑 Playwright 风险大（Chromium 单次峰值 300-600MB 堆外内存，易 OOM）→ 默认走 openhtmltopdf。
