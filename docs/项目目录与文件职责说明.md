# 项目目录与文件职责说明

本文按“仓库根目录 → Maven 模块 → Java 包 → 主要调用链”说明 NnmBot 当前文件结构。
它用于帮助定位代码，不替代具体业务文档。新会话应先阅读
[项目上下文与续作指南.md](项目上下文与续作指南.md)；模块依赖、编码规范和数据边界仍以
[项目架构与开发约定.md](项目架构与开发约定.md) 为准。

## 一、仓库根目录

```text
NnmBot/
├── pom.xml
├── mvnw / mvnw.cmd
├── .mvn/
├── scripts/
├── docs/
├── data/
├── logs/
├── nnm-common/
├── nnm-core/
├── nnm-render/
├── nnm-warframe/
├── nnm-admin/
└── nnm-app/
```

| 路径 | 职责 | 是否属于业务源码 |
| --- | --- | --- |
| `pom.xml` | Maven 父工程，统一 Java 版本、依赖版本、模块顺序和插件配置。 | 是 |
| `.mvn/`、`mvnw` | Maven Wrapper，使本地和 CI 使用一致的 Maven 启动方式。 | 是 |
| `scripts/run-dev.sh` | 编译当前 Reactor 后启动 `nnm-app`，避免误用本地仓库中的旧模块 JAR。 | 是 |
| `scripts/database/` | 数据导入、SQL 生成和 SQL 校验脚本；不是应用启动时自动执行的迁移。 | 是 |
| `docs/` | 当前架构、业务规则、接入方式和续作说明。 | 是 |
| `docs/sql/init.sql` | PostgreSQL 完整初始化基线，负责创建 `nnmbot` schema、表、索引、约束和初始数据。 | 是 |
| `docs/sql/01_*.sql` 等 | 已有数据库需要手工执行的增量修复脚本。 | 是 |
| `docs/README.md` 及根目录说明文档 | 给后续开发会话使用的现行架构、数据追溯和实现差距说明，不是运行时配置。 | 是 |
| `data/` | 本地开发运行生成或下载的数据，例如 JMComic、Warframe 论坛文件。 | 否，通常不提交 |
| `logs/` | 本地日志输出。 | 否 |
| `.run/` | IDE 本地运行配置。不得放密码、令牌等敏感信息。 | 辅助配置 |
| `.idea/` | IntelliJ IDEA 工作区配置。 | 否 |
| `target/`、`*/target/` | Maven 编译产物、测试报告和生成文件，可随时重新生成。 | 否 |

## 二、模块职责

### 1. `nnm-common`

与具体机器人渠道和 Warframe 业务无关的稳定基础能力。

主要目录：

| 包 | 职责 |
| --- | --- |
| `common.error`、`common.constant` | `ErrorCode` 契约和公共错误码。 |
| `common.exception` | 业务异常、系统异常、外部调用异常和全局异常转换。 |
| `common.response` | 统一 API 响应 `ApiResponse` 和分页结果 `PageResult`。 |
| `common.validation` | `BusinessAssert` 等业务前置条件校验。 |
| `common.config.http` | HTTP 超时、重试、TLS、响应体大小等配置和 `RestClient` 装配。 |
| `common.http` | 外部 HTTP 调用入口、客户端工厂、响应限制和异常归一化。 |
| `common.config.ocr`、`common.ocr` | OCR 配置、接口和 RapidOCR 实现。 |
| `common.retry` | 与具体上游无关的退避计算。 |
| `common.task` | 后台长任务状态、进度和提交接口；具体存储实现在 `nnm-core`。 |
| `common.web` | 与业务无关的 Web 请求模型。 |

边界要求：

- 不依赖 `nnm-core`、`nnm-warframe`、`nnm-admin` 等业务模块。
- 不放机器人命令、Warframe DTO、Redis owner 或数据库实体。
- 没有实际调用点的工具类不提前迁入本模块。

### 2. `nnm-core`

机器人运行内核，负责渠道连接、消息上下文、命令执行、群组积分、JMComic 和 RDT 集群协调。

主要目录：

| 包 | 职责 |
| --- | --- |
| `core.channel.model` | 跨渠道共用的机器人实例键、状态快照和群组发现结果。 |
| `core.channel.port` | `nnm-core` 依赖的端口接口，由 `nnm-admin` 等外层模块适配数据库实现。 |
| `core.channel.registry` | 当前实例已经建立的机器人连接注册表。 |
| `core.channel.runtime` | 机器人连接启停、Redis owner lease、跨实例状态读取和群组发现协调。 |
| `core.channel.messaging.model` | 跨实例渠道消息的稳定载荷。 |
| `core.channel.messaging.producer` | 使用 RDT 编程式 API 投递渠道消息。 |
| `core.channel.messaging.consumer` | 一类一消费者的 RDT 声明式消费者。 |
| `core.channel.messaging.store` | 跨实例请求与响应之间的短期共享状态。 |
| `core.onebot` | OneBot 配置、WebSocket 连接、事件转换、发送和响应策略。 |
| `core.qqofficial` | QQ 官方机器人 API、Gateway WebSocket、消息转换和响应策略。 |
| `core.message.model` | 渠道无关的消息上下文、附件、文件和 Markdown 模型。 |
| `core.message.sender` | 主动消息的渠道路由。 |
| `core.plugin.api`、`core.plugin.annotation` | 命令插件契约和声明元数据。 |
| `core.plugin.registry` | 插件扫描、命令与别名注册、唯一性校验。 |
| `core.plugin.execution` | 命令匹配、权限、冷却、积分、异常和执行流水线。 |
| `core.plugin.response` | 将 `CommandResult` 路由到具体渠道的响应策略。 |
| `core.group` | 群组、成员、积分账户和群组系统命令。 |
| `core.jmcomic` | JMComic 下载、整本文件、PDF 和机器人命令。 |
| `core.task` | 后台管理任务的本地或 Redis 实现。 |
| `core.config` | 统一执行器、分布式开关和本模块配置。 |

典型消费者：

```text
nnm-core/src/main/java/com/nnm/bot/core/channel/messaging/consumer/
└── OneBotScopeDiscoveryMessageConsumer.java
```

它在类上声明 `@RdtQueueListener`，实现 `RdtMessageConsumer<OneBotScopeDiscoveryRequest>`，
只负责一个 OneBot 群组发现订阅。

### 3. `nnm-render`

将结构化展示数据转换为 HTML、图片或 PDF，不负责查询 Warframe 数据或判断机器人权限。

主要目录：

| 包或路径 | 职责 |
| --- | --- |
| `render` 根包 | `ImageService`、`TemplateRenderer`、`RenderEngine` 等稳定接口。 |
| `render.config` | 渲染引擎、Playwright 和外部插件配置。 |
| `render.engine` | OpenHTMLToPDF、Playwright 等具体引擎。 |
| `render.impl` | 模板渲染和图片服务实现。 |
| `render.spi` | 受控的外部渲染引擎扩展点。 |
| `src/main/resources/templates` | 受版本管理的 Thymeleaf 模板；当前为空时表示主要使用数据库或内联模板。 |

渲染输入应是已经整理好的展示 DTO，不能在模板中重新请求外部接口或解析原始 WorldState。

### 4. `nnm-warframe`

Warframe 领域模块，包含外部客户端、解析、缓存、数据库、命令插件和后台管理接口。

主要目录：

| 包 | 职责 |
| --- | --- |
| `warframe.client` | 面向业务的外部客户端，处理调用结果和业务级异常。 |
| `warframe.client.exchange` | `@HttpExchange` HTTP 协议接口，只描述请求路径、参数和响应。 |
| `warframe.config` | HTTP 代理创建、缓存和论坛相关装配。 |
| `warframe.config.properties` | 外部地址、超时、刷新周期、缓存容量和保留时间。 |
| `warframe.parser` | 将外部 JSON、PublicExport 或社区数据转换为内部模型。 |
| `warframe.model` | 与持久化无关的业务请求、结果和 WorldState 模型。 |
| `warframe.model.entity` | JPA 实体，只表达数据库结构和必要关联。 |
| `warframe.repository` | Spring Data JPA 查询。 |
| `warframe.application` | 对外稳定的应用服务接口、编排对象和跨子域协作。 |
| `warframe.service` | 细分领域服务接口及领域协调组件，例如来源并行加载和数据集锁。 |
| `warframe.service.impl` | 应用服务和领域服务的具体实现。 |
| `warframe.service.catalog` | 被业务 Service 调用的数据集定义与来源登记；不承载命令业务编排。 |
| `warframe.cache` | Redis 共享快照、社区预览分片存储与压缩、生命周期清理、本地索引失效和缓存名称。 |
| `warframe.messaging.model` | RDT 消息载荷或本地事件载荷。 |
| `warframe.messaging.producer` | 编程式消息投递；业务代码显式决定何时发送。 |
| `warframe.messaging.consumer` | 类级声明的消息消费者；一个类只负责一个订阅。 |
| `warframe.plugin` | Warframe 机器人命令，负责参数解释、业务查询和展示 DTO 组装。 |
| `warframe.pojo` | 外部协议或内部中间结构；不作为数据库实体使用。 |
| `warframe.controller` | Warframe 管理端和公共 HTTP 接口。 |
| `warframe.constant` | 稳定的数据集编码、命令编码、来源类型和错误码。 |

消息消费者示例：

```text
nnm-warframe/src/main/java/com/nnm/bot/warframe/messaging/consumer/
└── WarframeWorldStateRefreshMessageConsumer.java
```

该类在类名上方声明 `@RdtQueueListener`，实现 `RdtMessageConsumer<String>`，在
`consume(String command)` 中执行世界状态刷新。生产者位于相邻的 `messaging/producer`，
发送和消费不会混在同一个类中。

社区刷新按职责分为四部分：`client/WarframeCommunityApiClient` 处理一个来源的 CDN 顺序回退；
`service/WarframeCommunitySourceLoader` 协调多个来源的并行下载、纯解析与失败摘要；
`service.impl/WarframeCommunityDatasetServiceImpl` 负责成功来源 diff、审核和数据库事务；
`cache/WarframeCommunityPreviewStore` 负责预览存储协议、分页范围读取及清理。失败来源保留原数据，
不进入新增、修改或删除候选。相关执行器由 `nnm-core/config/ExecutorConfig` 统一管理，
不在 Warframe Service 中新建线程池或把预览业务缓存迁入 common。

### 5. 业务模块内的调度任务

定时任务不单独建立 Maven 模块，按业务归属放在模块自己的 `task` 包。例如
WorldState 轮询和本地图片预热属于 `nnm-warframe/task`。任务类负责调度入口，
具体工作委托给同模块的 Service。

Warframe 集群任务采用统一结构：

```java
@Component
@RdtScheduled(
        id = "example-v1",
        cron = "0 0 4 * * *"
)
public class ExampleTask implements RdtScheduledTask {

    @Override
    public void execute() {
        // 调用业务 Service
    }
}
```

当前类级 RDT 任务包括：

- `WorldStatePollingTask`：触发 Warframe 世界状态刷新。

仲裁排期由管理端统一社区数据集主动刷新、预览并采纳，没有独立的排期自动写库任务。

以下任务保留 Spring 本地调度，因为每个实例都要处理自己的本地资源：

- `ArbitrationImagePrewarmTask`：预热当前 JVM 的本地图片缓存。
- `WarframeForumTemporaryFileCleanupTask`：清理当前实例的临时目录。

`LocalPollingTasks` 只在关闭分布式模式时提供单节点兜底，避免与 RDT 重复触发。

## 三、常见包名的判断方式

| 包名 | 应放内容 | 不应放内容 |
| --- | --- | --- |
| `controller` | HTTP 入参、权限、响应封装 | 复杂查询、事务编排、外部 HTTP 调用 |
| `application` | 跨服务编排、对上层稳定的用例接口 | HTTP 协议细节、JPA 查询实现 |
| `service` | 单一业务能力接口 | Controller DTO 拼装 |
| `service.impl` | 业务实现和必要事务边界 | 与业务无关的全局工具 |
| `client` | 上游业务客户端 | Controller、数据库写入 |
| `client.exchange` | 声明式 HTTP 协议 | 重试策略、业务落库 |
| `parser` | 外部格式到内部模型的纯转换 | 网络请求、数据库事务 |
| `model` | 业务模型、命令或查询结果 | JPA 注解实体 |
| `model.entity`、`domain` | 数据库实体 | 外部响应原样透传 |
| `repository` | 数据访问 | 命令文案和外部请求 |
| `config.properties` | 可配置值和启动校验 | 运行中不断变化的业务状态 |
| `messaging.model` | 稳定、可序列化的消息载荷 | Spring Bean 或业务 Service |
| `messaging.producer` | 编程式投递 | 消费逻辑 |
| `messaging.consumer` | 类级监听注解和消费逻辑 | 发送入口或多个无关订阅 |
| `plugin` | 机器人命令参数解释和结果组装 | 通用 HTTP、数据库基础设施 |
| `cache` | 明确生命周期的共享快照或本地派生缓存 | 可审计历史的唯一存储 |

## 四、主要运行链路

### 1. 机器人命令链

```text
OneBot / QQ 官方平台事件
  -> 渠道连接与协议解析
  -> BotMessageContext
  -> CommandDispatcher
  -> CommandRegistry 匹配命令
  -> CommandExecutionPipeline
  -> BotPlugin.handle()
  -> CommandResult
  -> CommandResponseDispatcher
  -> 渠道 ResponseStrategy
  -> 平台发送 API 或 WebSocket
```

渠道接入只负责协议转换；命令权限、冷却和积分集中在执行流水线；插件只处理当前命令。

### 2. RDT 集群定时任务链

```text
Spring 启动扫描
  -> 发现类级 @RdtScheduled
  -> 校验实现 RdtScheduledTask
  -> 按任务 id 注册或按策略刷新 Redis 定义
  -> 多实例竞争同一次触发
  -> 选中的实例调用 execute()
  -> 记录成功、失败和下一次触发时间
```

注解写在类名上方，不写在 `execute()` 方法上。任务类只负责调用业务 Service。

### 3. RDT 消息链

```text
业务 Service
  -> messaging.producer
  -> MessageQueueTemplate 编程式投递
  -> Redis Stream / Reliable Broadcast
  -> 类级 @RdtQueueListener
  -> RdtMessageConsumer<T>.consume()
  -> 业务 Service
```

生产者和消费者分文件存放。消费者正常返回后确认消息；抛出异常时由队列策略重试或进入死信，
业务副作用仍需依靠消息 ID 或业务唯一键保证幂等。

### 4. Warframe 世界状态刷新链

```text
WorldStatePollingTask
  -> WarframeWorldStateRefreshMessageProducer
  -> WarframeWorldStateRefreshMessageConsumer
  -> WarframeWorldStateService
  -> WarframeWorldStateHttpExchange
  -> WorldStateParser
  -> SharedWorldStateStore
  -> Redis 最新快照
  -> WarframeWorldStateUpdatedMessageProducer
  -> 各实例清理或重建本地读模型
```

外部刷新失败时不能覆盖最后一次成功快照。Redis 保存多实例共享的当前状态，本地 cache2k
保存可重建的派生查询结果。

### 5. Warframe 仲裁排期链

```text
管理端 Warframe 社区数据 -> arbitration_schedule
  -> WarframeCommunityDatasetService
  -> WarframeCommunitySourceLoader
  -> WarframeCommunityApiClient -> ArbitrationScheduleParser
  -> WarframeCommunityPreviewStore -> Redis 分片预览与来源摘要
  -> 管理员选择并采纳 -> WarframeArbitrationStore
  -> PostgreSQL wf_arbitration_schedule
```

机器人命令和图片预热只读 PostgreSQL 已采纳数据，不在查询时临时请求上游。
仲裁排期禁止人工新增、上传、修改和删除；查询、刷新和采纳仍可使用统一社区接口。

### 6. 管理端 API 链

```text
nnm-admin-web
  -> /api/admin/v1
  -> Controller + @SaCheckPermission
  -> Service
  -> Repository / core 端口 / Warframe application service
  -> ApiResponse
```

### 7. 图片渲染链

```text
BotPlugin 组装展示 DTO
  -> CommandResult.data
  -> BotImageRenderer / ImageService
  -> TemplateRenderer
  -> OpenHtmlToPdfEngine 或 PlaywrightEngine
  -> 图片/文件
  -> 渠道响应策略
```

## 五、定位代码时的建议顺序

1. 从命令名定位 `plugin`。
2. 查看插件调用的 `application` 或 `service` 接口。
3. 进入 `service.impl` 判断数据来自 HTTP、PostgreSQL、Redis 还是 cache2k。
4. 外部字段不明确时查看 `client.exchange`、`pojo` 和 `parser`。
5. 数据库问题查看 `model.entity`、`repository` 和 `docs/sql/init.sql`。
6. 多实例问题查看 `messaging`、`cache.SharedWorldStateStore`、`channel.runtime` 和
   `application-distributed.yml`。
7. 返回内容或图片不正确时查看展示 DTO、`CommandResult`、模板和 `nnm-render`，不要先改数据源。
