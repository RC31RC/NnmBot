## 2. 当前状态

### 2.1 外部 HTTP 请求

- NnmBot 使用 Spring `RestClient`，底层为 Java 21 `HttpClient`。
- GET 已支持连接超时、读取超时、429/5xx 和网络异常重试，重试使用有上限的指数退避。
- `nnm.http.*` 和 `nnm.warframe.api.*` 已使用 `@ConfigurationProperties` 集中管理并在启动时校验。
- 世界状态轮询开关和间隔由 `nnm.warframe.polling.*` 集中管理，自动化测试关闭外部轮询。
- `WarframeApiClient` 当前按配置请求 Warframe 官方 WorldState 和 `warframe.market`；
  `WorldStateProvider` 只保留一个官方适配实现，暂不实现备用数据源。
- 当前没有代理地址、代理认证和非代理地址配置。
- `trustAllCerts` 当前默认值为 `false`；只允许在定位本地代理或证书链问题时临时开启。
- 世界状态轮询通过 `WorldStateProvider` 获取官方原始 JSON，再由 `WorldStateParser` 转换为
  NnmBot 领域模型；当前不负责维护上游数据，只负责协议适配。

### 2.2 缓存和会话

- `nnm-warframe` 已引入 cache2k、Caffeine 和 Spring Cache。
- 显式 `SpringCache2kCacheManager` 是当前生效的 JVM 业务缓存管理器。
- Caffeine 依赖及 `maximumSize=500,expireAfterWrite=600s` 配置按要求暂时保留，但不承载业务缓存。
- 已建立四个命名缓存区域；当前业务解析和 loader 尚未完成，因此还没有实际业务数据写入。
- Sa-Token 没有配置 Redis 或自定义 `SaTokenDao`。
- Sa-Token 当前使用自身默认的 JVM 进程内存储，不使用 Caffeine。
- 应用重启后，当前登录 Token 和会话映射失效，用户需要重新登录。

## 3. 代理边界

### 3.1 代理的实际位置

代理不是 Digital Extremes 或 Warframe API 提供的业务 URL，而是 NnmBot 自己选择的网络出口：

```text
用户/QQ群
    -> NnmBot
        -> 指定的 HTTP 代理
            -> Warframe API / Warframe.market / 数据 CDN
```

用户只访问机器人或 NnmBot 管理接口，不接触代理地址。NnmBot 不提供允许用户指定任意目标
URL 的通用代理接口，避免形成可被滥用的开放代理。

代理认证取决于代理服务：

- 本机代理通常使用 `127.0.0.1:端口`，可能不需要认证；
- 商业代理可能使用用户名和密码；
- 部分代理使用服务器出口 IP 白名单；
- 代理密码只能通过环境变量或外部配置注入，不能提交到 Git。

### 3.2 NnmBot 的目标实现

不复制 NyxBot 自动读取所有系统代理并全局生效的方式。NnmBot 使用显式、类型安全的配置，
并允许按外部系统决定是否走代理。

建议配置边界：

```yaml
nnm:
  warframe:
    proxy:
      enabled: false
      type: http
      host: 127.0.0.1
      port: 7890
      username:
      password:
      non-proxy-hosts:
        - localhost
        - 127.0.0.1
```

第一阶段只支持经过实际验证的 HTTP CONNECT 代理。SOCKS5 需要单独实现并进行集成测试，
不能仅通过解析 `socks5://` 字符串宣称支持。

## 4. GitHub/CDN 数据适配

### 4.1 NyxBot 的作用

NyxBot 从 GitHub 仓库解析数据版本，再构造多个 jsDelivr/CDN 和自建站点地址，并发请求这些
地址，使用第一个成功且能够解析的数据。

这些文件主要不是实时世界状态，而是经过维护和标准化的静态数据，例如：

- 物品别名和中英文映射；
- 星图节点；
- 奖励池；
- 世界状态翻译；
- 紫卡词条、倾向和趋势；
- 其他不能直接按官方原始结构用于机器人展示的数据。

GitHub 在这里承担版本、历史、审核和回滚职责，CDN 承担分发和备用线路职责。数据的难点
通常不是发出 HTTP 请求，而是持续处理上游字段变化、中文翻译、别名、去重、校验和版本更新。

### 4.2 NnmBot 当前边界

数据源提供者由第三方维护，NnmBot 当前只负责适配，不提前实现备用来源或自建数据服务。
初期链路为：

```text
官方 API / PublicExport / 可信社区数据
    -> WorldStateProvider / 静态数据适配器
    -> 结构校验、标准化
    -> NnmBot 领域模型
    -> 本地缓存提供高频读取
```

GitHub/CDN 可以保留为初始化来源、更新来源或故障备用来源，但不能在没有校验的情况下直接让
“最新 tag”覆盖当前可用数据。

每次导入至少记录：

- 数据类型；
- 来源和来源版本；
- 抓取时间；
- 数据版本；
- 内容校验和；
- 记录数量；
- 校验状态；
- 失败原因；
- 当前是否为生效版本。

## 5. Warframe 数据结构边界

NyxBot 使用 `WorldState`、`ActiveMission`、`VoidTrader`、市场订单和各类枚举等自定义 Java
模型，把外部 JSON 转换成可以直接表达 Warframe 业务概念的对象。这不是官方数据库结构，
而是面向外部接口的 DTO/模型库。

NnmBot 不直接把 NyxBot 的模型包作为核心领域和 JPA 实体，统一采用以下边界：

```text
外部响应 DTO
    -> Parser / Mapper / Validator
        -> NnmBot 领域模型
            -> JPA Entity / Read Model
                -> 管理端或机器人响应 DTO
```

约束：

- 外部 JSON 字段变化只影响 DTO 和适配层；
- 领域模型使用 NnmBot 自己的业务命名和约束；
- JPA 实体只负责持久化，不直接承载外部 API 协议；
- 字段较多且映射稳定时使用 MapStruct；
- 时间转换、枚举兼容、奖励归类等复杂规则使用显式代码和测试；
- 不在业务代码中传播原始 `Map<String, Object>`。

## 6. cache2k 与 Caffeine 的最终选择

### 6.1 当前业务需要的缓存能力

NnmBot 的主要缓存不是通用 Web 页面缓存，而是外部数据源缓存：

- 世界状态只有一个当前值，需要定时刷新；
- 外部 API 失败时需要继续提供最后成功值；
- 静态数据刷新失败时不能影响已有查询；
- 不同数据源的 TTL 差异明显；
- 用户可见的 Market 订单和拍卖数据可能随时变化，默认要求每次命令重新请求；
- 同一时刻相同 Market 请求可以合并为一次出站请求，但响应完成后不复用；
- GitHub tag、数据版本和翻译数据需要较长 TTL；
- 需要避免同一 Key 并发触发多次外部请求；
- 需要记录加载、刷新、失败和旧值命中状态。

### 6.2 不考虑切换成本时的结论

**目标 JVM 本地缓存选择 cache2k。**

选择 cache2k 不是因为 NyxBot 已经使用它，而是因为当前业务以“有明确 loader 的外部数据、
刷新失败继续使用旧值、按数据源动态过期”为主。cache2k 的 loader、refresh-ahead、
resilience、异常抑制和单条过期能力更直接地表达这些需求。

Caffeine 的 W-TinyLFU、高并发读写和异步缓存更适合大量 Key、访问热度差异明显、重点追求
命中率的通用进程内缓存。NnmBot 会有 Market 查询的并发合并，但不保留完成后的订单响应，
因此它不是整个缓存体系的主导需求。
对于容量为 1 的世界状态和数量有限的静态数据，淘汰算法优势基本没有发挥空间。

因此，在完全忽略现有依赖和迁移成本的前提下：

| 场景 | 更适合 |
| --- | --- |
| 世界状态定时刷新、失败保留旧值 | cache2k |
| 静态数据 loader、刷新和异常抑制 | cache2k |
| 每条记录使用不同过期时间 | cache2k |
| 大量非实时查询 Key 的热点淘汰 | Caffeine |
| NnmBot 整体业务模型 | cache2k |

当前只允许 cache2k 承载 JVM 业务缓存。Caffeine 依赖和 YAML 配置仅为本阶段比较、回退而
暂时保留，不允许同时在 Caffeine 上新增业务缓存；评估结束后再删除。Sa-Token 默认内存 DAO
不属于业务缓存，不受该选择影响。

### 6.3 当前已配置的缓存区域

| 缓存区域 | 当前容量 | 当前生命周期 | 接入业务后的故障策略 |
| --- | ---: | --- | --- |
| `warframeWorldState` | 1 | 常驻，由轮询成功结果覆盖 | 返回最后成功值并标记陈旧 |
| `warframeMetadata` | 64 | 写入后 6 小时 | 保留最后成功版本 |
| `warframeTranslations` | 16 | 写入后 12 小时 | 保留最后成功版本 |
| `dataSourceTag` | 8 | 写入后 2 分钟 | 使用最近成功 tag |

配置统一禁止缓存 `null`、启用统计并拒绝动态创建未知缓存。拒绝未知缓存可以让缓存名拼写错误
在开发阶段直接暴露，而不是静默创建一个没有容量和生命周期约束的新区域。

`warframeWorldState` 当前常驻是为了配合已有的两分钟定时轮询：只有成功结果才覆盖，失败时
保留最后成功值。业务接入后仍必须额外记录数据抓取时间和“新鲜/陈旧”状态，常驻不代表结果
永远新鲜。其他区域在接入 loader 后可再根据真实数据量和上游更新频率调整。

不能只配置全局 `entryCapacity`。每个缓存区域必须显式设置容量、过期、loader 和故障策略。
对大型响应除条目数量外还要限制响应大小；必要时使用 `Weigher`/`maximumWeight` 约束估算
内存，或者只缓存解析后的摘要和索引，因为 `entryCapacity` 只限制条目数，不限制每条大小。

Market 订单、紫卡拍卖和赤毒/信条拍卖不属于以上持久缓存区域。它们需要每次面向用户的查询都
访问上游 API；同一时刻完全相同的请求可以使用 single-flight 合并出站调用，但结果发送后立刻
释放。上游不可用时可以返回上一次成功结果作为明确标注“数据可能过期”的降级响应，但该能力
必须由产品开关控制，不能替代默认的实时查询。

### 6.4 cache2k 特殊能力在 NnmBot 中的使用位置

| cache2k 能力 | 当前项目适用位置 | 使用边界 |
| --- | --- | --- |
| `CacheLoader` | 世界状态、物品元数据、翻译、数据源 tag | 把“没有值时如何获取”集中到基础设施层；领域服务只依赖 Spring Cache 或仓储接口 |
| `refreshAhead` | 高频访问的世界状态、别名和翻译索引 | 在过期前后台刷新，避免第一个用户等待；必须先配置 loader，不用于实时 Market 订单 |
| `ResiliencePolicy` | Warframe API、GitHub/CDN、静态数据导入读取 | loader 失败时抑制异常并继续使用最后成功值，同时设定重试时间；响应必须标记数据时间和陈旧状态 |
| loader 并发合并 | 同一版本元数据、同一语言翻译、同一 tag | 同一个 Key 并发未命中时只执行一次加载，防止缓存击穿 |
| `ExpiryPolicy` | 活动、警报、虚空商人等具有自身结束时间的数据 | 根据每条上游数据的结束时间动态过期，不必把所有条目套在同一个 TTL 上 |
| `sharpExpiry` | 到点后绝不能继续当作有效结果的事件索引 | 更接近指定时间失效；仍需允许少量调度误差，不能作为交易或权限的一致性机制 |
| `keepDataAfterExpired` | 世界状态和静态数据的重新加载过程 | 保留过期条目供 loader、expiry 或 resilience 判断旧值；它不表示普通 `get` 会直接返回过期值 |
| `BulkCacheLoader` | 一次下载后生成的别名、节点、奖励池和翻译索引 | 一次上游请求填充多个 Key，减少重复下载；导入结果仍以 PostgreSQL 当前生效版本为准 |
| `invoke`/EntryProcessor | 缓存内版本指针、局部计数和状态原子切换 | 适合单 JVM 原子更新；持久业务状态、权限和通知幂等仍由 PostgreSQL 保证 |
| `Weigher`/`maximumWeight` | 大型 JSON、翻译 Map、奖励池索引 | 按估算重量限制内存，比只按条目数更适合 4GB 机器；需要先定义可测试的重量算法 |
| 统计与监听器 | Actuator 自定义指标、管理端数据源状态 | 记录命中、加载、刷新和异常；cache2k 指标需显式接入 Micrometer，不能假设自动出现 |
| 自定义 executor 和线程数 | 外部数据 loader、refresh-ahead | 使用小型有界执行器，避免缓存刷新与渲染、调度任务争抢 4GB 服务器资源 |

其中最有价值的是 loader、refresh-ahead 和 resilience 的组合：

```text
读取缓存
  -> 有新鲜值：立即返回
  -> 即将过期：返回当前值，并由 refresh-ahead 后台刷新
  -> loader 失败：按 ResiliencePolicy 延迟重试，继续提供最后成功值
  -> 超过允许陈旧窗口：返回不可用，不再伪装成实时数据
```

该组合适用于世界状态和低频变化的静态数据。`keepDataAfterExpired` 只是让旧条目留在内部供
加载和容错决策使用，真正“失败后继续返回旧值”必须由 loader 与 `ResiliencePolicy` 共同
定义，并由业务响应携带抓取时间和陈旧标记。

对 `@Cacheable(sync = true)`，cache2k 的 Spring 适配器会通过原子
`computeIfAbsent` 合并同 Key 的并发加载，适合元数据和翻译。Market 订单不能直接使用这种
普通缓存，因为加载完成后的值仍会按 TTL 留存；Market 应实现独立的 `CompletableFuture`
single-flight 注册表，请求结束立即移除。

以下能力暂不建议使用：

- CacheWriter 直写 PostgreSQL：缓存不能成为数据源，静态数据仍应先完成校验和事务提交；
- 将权限、Sa-Token 会话放入业务缓存：两者有独立的一致性和生命周期要求；
- 无容量缓存或一个全局大缓存：无法控制 4GB 服务器的最坏内存占用；
- 对所有数据启用 refresh-ahead：低频 Key 会制造没有用户价值的后台请求。

## 7. Caffeine 与 Redis 的容量说明

Caffeine 是 JVM 进程内缓存，不是本地数据库；Redis 是独立的内存数据存储。

如果完全排除框架、进程、索引、Key、TTL 和条目元数据，只比较相同业务数据的原始字节，
两者能够保存的数据量相同。实际运行时不能这样比较，因为两者的数据表示不同：

- Caffeine 保留 Java 对象及对象图，不需要网络和序列化；
- Redis 保存序列化后的字符串、字节或 Redis 数据结构；
- 复杂 Java 对象可能比序列化后的 JSON/二进制更大；
- Redis 每个独立 Key、TTL 和字典节点也有额外开销；
- 大量小 Key 和少量大型对象会得到不同结果。

因此不能用“同样 100MB 谁一定存得更多”作为选型依据。当前项目选择本地缓存，是因为单实例、
低延迟、无需序列化和运维简单；不是因为本地缓存对所有数据结构都一定更节省内存。

## 8. Sa-Token 与 Redis

当前 Sa-Token 会话保存在 Sa-Token 默认 JVM 内存 DAO，不在 cache2k 或 Caffeine 中。单机
阶段继续保留该实现，接受应用重启后管理员重新登录。

不为以下需求单独引入 Redis：

- 少量管理端会话；
- 单实例登录检查；
- 普通 Warframe 数据缓存；
- 可以接受重启后重新登录的开发和初期生产环境。

满足以下任一条件时重新评估 Redis：

- NnmBot 部署多个实例；
- 滚动重启期间必须保持登录；
- 需要跨实例踢人、黑名单和在线会话；
- 需要分布式限流、锁、队列或跨进程缓存；
- 单机进程内缓存已无法满足数据规模或生命周期要求。

## 10. 验收标准

完成上述任务后，应满足：

1. 未配置代理时可以直连；配置代理后只有指定外部客户端走代理。
2. 代理故障不会泄露用户名和密码，日志能够定位目标、耗时和错误类别。
3. 外部世界状态短时不可用时，机器人可以返回带数据时间的最后成功结果。
4. 静态数据更新失败时，当前生效版本不受影响。
5. 每类缓存都有明确容量、过期、刷新和故障策略。
6. 应用重启后业务静态数据可以从 PostgreSQL 恢复，登录用户重新登录。
7. 4GB 服务器上缓存、JVM、PostgreSQL 和渲染进程不会发生无界内存增长。
