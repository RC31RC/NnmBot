# 多渠道实例与群组回复路由

本文描述当前实现，不代表已完成真实平台账号的上线验收。
`nnm.bot.channels` 保持不变，尤其不把 OneBot 的 WS 文件发送配置套到 QQ 官方渠道。

## 渠道实现边界

OneBot 复用 Shiro 的协议模型，实例连接由本项目管理。QQ 官方由 JDK WebSocket Gateway 和 REST 适配器实现；当前仓库未实现 Webhook 接入。每个实例独立持有客户端、令牌和连接状态；实际账号能力需要实机验证，不能由本地代码支持推断平台已授权。

QQ 群/C2C 的文件实现通过上传得到 `file_info` 再发送；频道按能力拒绝文件。QQ 群发现依赖已观察到的 `group_openid`，不能当作机器人所在全部群组枚举。成员查询能力与群组枚举能力分开判断。

## 2. 配置与独立启停

现有数据库已实现按渠道拆表，不需要把不同渠道字段塞进公共 JSON：

| 表 | 主要字段 |
| --- | --- |
| `nnmbot.bot_channel_instance` | `platform`、`instance_id`、`display_name`、`bot_account_id`、`enabled` |
| `nnmbot.bot_onebot_config` | `connection_url`、`access_token`、`reconnect_interval_seconds` |
| `nnmbot.bot_qq_official_config` | `app_id`、`client_secret`、`token_url`、`api_base_url`、`gateway_url`、`intents`、`gateway_connect_timeout_seconds`、`reconnect_delay_seconds` |
| `nnmbot.bot_group_bot` | 实例与逻辑群的绑定、`enabled`、新增 `reply_priority` |

管理端已有的渠道表单和独立启停入口继续使用。公共运行期 record 是配置快照，
不是数据库存储模型；增加渠道时优先扩展对应配置实体、Provider 和 Connector。
单实例停止会取消心跳、READY 超时、重连并关闭本实例连接/客户端，不影响其他实例。
QQ 只有 READY/RESUMED 后才报告 CONNECTED，旧 socket 回调不能改变新连接状态。

## 2.1 渠道能力

`BotChannelCapability` 是公共能力链路的唯一声明入口，运行时注册表保存每个实例的能力快照，
发现、成员同步和回复路由都先经过能力过滤：

| 能力 | OneBot | QQ 官方 | 语义 |
| --- | --- | --- | --- |
| `TEXT_MESSAGE`、`IMAGE_MESSAGE`、`FILE_MESSAGE` | 支持 | 支持群/C2C；频道按会话拒绝文件 | 输出消息 |
| `MARKDOWN_MESSAGE` | 由策略降级文字 | 支持 | 输出消息 |
| `GROUP_DISCOVERY` | API 全量群组列表 | Gateway 观察到的群组 | 发现作用域 |
| `GROUP_LIST` | 支持 | 不声明 | 平台全量列出机器人所在群组 |
| `GROUP_MEMBER_LIST`、`GROUP_MEMBER_DETAIL` | 支持 | 支持，但可能需要白名单 | 查询已知群组成员 |
| `GROUP_MEMBER_EVENTS` | 支持 | 支持，需订阅 `1 << 24` | 成员加入、退出 |
| `BOT_GROUP_MEMBERSHIP_EVENTS` | 按平台事件适配 | 支持 | 机器人入群、退群 |

这一区分避免把“能收到群成员事件”“能查询已知群成员”和“能列出机器人所有群组”混成一个能力。
公共管理流程只依赖 `BotScopeDiscoveryProvider`、`BotGroupMemberEventSink` 和能力枚举，
平台适配器负责把协议事件转换为统一的作用域和成员模型；发现结果仍必须由管理端确认后写入绑定。

QQ 的实际流程是：机器人入群或收到群消息 -> Gateway 观察并保存 `group_openid` -> 管理端发现 ->
按已知 `group_openid` 查询成员（权限不足则保留增量结果）-> 选择逻辑群组 -> 写入
`bot_group_bot.scope_key`。QQ 没有提供可替代这一流程的机器人群组全量枚举接口。

## 3. 入站归并与执行

```text
原生消息及本机接收时间 → 内存匹配 → 有界非等待接纳 → 应用执行器
  → owner/代际/期限复核 → 最新配置与逻辑成员上下文 → 原生身份及接收轮次关联
  → 权限校验 → 本地认领 → 冷却/积分预占 → 插件执行一次
  → 业务结果 → 可行方案选择唯一实例 → 准备并有序投递 → 独立投递状态
```

连接分组使同一逻辑群相关实例落在同一 owner 节点，归并、认领与冷却使用有界本地状态。
关联采用逻辑群、主成员、规范命令/参数、原生账号/消息身份及本机接收时间跨度，保留多轮，
不是固定时间桶或仅按相同文本合并。同账号不同原生 messageId 可形成两次真实发送；
后到回执补充发送/绑定身份，不重新执行或重发。极近连续发送与跨平台乱序仍有歧义，
不承诺跨进程崩溃 exactly-once。未匹配不排队；入站拒绝或执行前过期不认领、不扣费。

QQ 官方用户标识按机器人实例区分。同一逻辑群组当前最多绑定一个 QQ 官方实例，包括被禁用的绑定；
成员继续保留现有 QQ/OpenID 字段，跨渠道调用需要先完成成员身份关联。
不可变 `CommandExecutionContext` 显式传递群组、绑定及主成员视图，权限、冷却和回复共用入口解析；
涉及积分、退款与身份合并的写入重新读取必要条件，不使用入口余额作最终扣费依据。

默认值由 `CommandRoutingProperties` 和 `BotCacheProperties` 提供；需要差异化调整时在 `application-system.yml` 覆盖：

| 属性 | 默认 | 用途 |
| --- | --- | --- |
| `nnm.bot.routing.correlation-window` | `3s` | 按接收时间跨度关联轮次的窗口 |
| `nnm.bot.routing.receipt-retention` | `2m` | 本地回执及轮次认领保留时间，至少覆盖关联窗口 |
| `nnm.bot.routing.max-pending-commands` | `2048` | 窗口、回执及轮次认领各自的有界容量 |
| `nnm.cache.bot.replay-retention` | `10m` | 当前 JVM 原生消息短期重复检查 |
| `nnm.cache.bot.replay-capacity` | `16384` | 原生消息记录容量 |
| `nnm.cache.bot.cooldown-retention` | `24h` | 本地交互冷却记录最长保留时间 |
| `nnm.cache.bot.cooldown-capacity` | `8192` | 本地冷却容量 |

容量或有效期耗尽后允许重新处理；这些本地状态不跨进程和节点接管保留。
数据库积分流水幂等与运行 owner 租约仍然生效，业务强一致性不依赖本地窗口。

## 4. 单一回复路由

命令回复和主动通知复用目标筛选及消息规划，检查绑定启用、实例启用、CONNECTED、
集群 owner 和 `reply_priority`。命令还检查本轮原生上下文及机器人命令权限；通知建立独立的
主动发送上下文，不借用命令的被动回复资格。

管理端群组绑定可设置启用与回复优先级，0 至 10000，默认 100，数值越小越优先；
相同值按绑定 ID 稳定排序。API 为：

```text
PUT /api/admin/v1/bot-groups/{groupId}/bots/{bindingId}
{"enabled":true,"replyPriority":10}
```

后端要求 `bot:group:update`，并校验绑定属于指定群组。
候选必须是启用绑定、启用实例、CONNECTED 且由本节点拥有。
回复模型是有序逻辑消息、内容块和消息级动作。`PresentationPolicy` 控制视图格式偏好、
组合与交互，并支持平台/会话 overrides；精确会话覆盖优先于平台全部会话，再使用默认策略。

- 业务结果形成后，按候选实例、会话和展示策略判断完整方案是否可行，再选唯一实例。
- 没有图片能力但允许文字回退时仍可候选；必要图片或文件不能表示时拒绝该方案，不能丢正文。
- `SUMMARY_ONLY` 只影响数据视图，直接图片和必要文件不因偏好被静默丢弃。
- QQ 被动回复需要本轮属于该账号的原生回执；等待结束仍不可用时跳过，不借其他渠道 messageId。
- OneBot 可按合法逻辑群绑定构建发送目标；无平台成员身份时不伪造 @。
- 规划器准备必要资源和消息后再有序投递；REQUIRE_SINGLE 不会悄悄拆分。
- 业务状态与逐条 DeliveryReport 分开记录；平台接受不等于用户已读。必要正文确定未发出才
  触发相应退费，部分接受或未知不自动重发、退款。

候选降级只发生在发送开始前。一旦开始投递，不因超时或异常改由另一实例重发；
因为平台可能已收到部分内容，也不再追加第二条失败通知。
失败需查看日志，平台请求不支持本项目租约 fencing，网络副作用无法撤销。

## 5. 多节点连接放置

群组发现的跨节点请求载荷现在携带 `platform`，消费者按 `BotLocalScopeDiscoveryProvider` 选择
持有目标实例的渠道适配器；现有 OneBot 队列名称保持兼容。新增渠道只需提供本地发现实现，
不再让集群协调器直接依赖 OneBot Provider。

启用逻辑群的启用绑定形成实例连通分量。同分量先竞争共享 affinity lease，
再竞争每账号 owner lease，让同群多个渠道连接及回执落在同一 JVM。
例如 A/B 同群、B/C 同群时，A/B/C 必须同节点，而不是按单个群独立放置。

续期、释放、回调和发送检查 acquisition-specific token；账号和 affinity 都有效
才允许使用连接。同节点内的拓扑变化自动更新亲和租约并保留 socket；新增绑定、重新启用绑定
或群组导致跨节点迁移时，先只读预检查，管理员确认后才保存。取消不保存；提交时校验确认标识
和当前所有权，方案变化需要重新确认。迁移只停止来源节点的相关连接，目标节点已有连接保留。
普通故障仍在租约过期和协调周期后自动接管。Redis/DB 不确定时 fail-closed。
节点身份失效会先清理旧消费者和连接，再自动重取租约并恢复，不要求重启 JVM。
启停是独立期望状态，不因同分量而同时启停其他机器人。

这实现连接亲和，不是跨 JVM 原生消息对象转发，也不是按流量均衡连接。
大连通分量会集中内存/网络开销，部署前应结合 4GB 总预算及数据库连接池 5 评估。

## 6. 升级与验证

新空库只执行 `docs/sql/init.sql`，已包含优先级、范围校验与单一逻辑群归属约束。
原 01～05 已合并并删除，后续过程脚本从新的 `01_*.sql` 开始，应用不会自动迁移。
已有库新增结构变更前先备份、停止并发绑定，并核对实际结构；历史跨群重复绑定必须
人工确定真实归属，不能通过删除绑定来绕过唯一约束。

```sh
sh mvnw -pl nnm-app -am test
sh mvnw -pl nnm-core -am -Dtest=MultiChannelRedisIntegrationTest \
  -Dsurefire.failIfNoSpecifiedTests=false -Drdt.it.redis=redis://127.0.0.1:16391 test
node scripts/database/verify-bot-reply-routing.cjs
node scripts/database/verify-warframe-sql.cjs --hibernate
```

Redis 集成测试需要显式准备隔离测试服务；使用随机命名空间，不清空 Redis。
该测试覆盖双客户端竞争、同群连接亲和、独立停止、租约过期接管，以及跨渠道单一执行权。

RDT 需安装提供批量租约读取、TTL 字段更新和可靠广播的本地运行时版本，步骤见
[RDT 接入与多实例运行](RDT接入与多实例运行.md)。
前端继续使用 `localhost:3006`，后端开发端口 8080，不执行生产打包。

上线前需用真实账号补充验收：两渠道同群归并、连续同文命令、文件转发、
QQ Markdown、首选离线、跨节点接管、Redis 断连及拓扑改变。
单元测试、模拟管理端与隔离 PostgreSQL/Redis 测试不能替代真实平台验收。

完整启动、绑定、关联、权限、积分及异常场景见 [运行流程与本轮改造说明](项目架构与开发约定.md)。
