# 机器人集群与多实例部署演进方案

## 1. 当前决策

当前版本只实现单进程内的多机器人实例，不实现机器人集群，也不提前引入 Redis。数据库保存
静态连接配置，应用启动时加载；WebSocket 会话、渠道状态和 Shiro Bot 对象保存在当前 JVM。

“多个账号随机回复”不能作为规避平台风控的保证。未来集群的首要目标应是消息幂等、连接
唯一归属、故障转移和可观测的负载分配。账号选择策略只能在平台规则允许的范围内降低单账号
压力，不能掩盖或放大自动化行为。

## 2. 何时启动集群改造

满足以下任一条件时再进入实施：

1. NnmBot 需要运行两个或更多应用节点；
2. 单个机器人账号需要在节点故障后自动漂移；
3. 多个机器人账号需要共享同一组消息处理规则并提供故障转移；
4. Sa-Token 会话、限流和消息幂等必须跨 JVM 一致。

在此之前继续保持 PostgreSQL + JVM 状态，避免为尚不存在的分布式边界增加维护成本。

## 3. 目标模型

```text
BotCluster
  id / name / enabled / reply_policy
       |
       +-- BotChannelInstance A (ONEBOT)
       +-- BotChannelInstance B (ONEBOT)
       +-- BotChannelInstance C (QQ_OFFICIAL)
```

协议配置仍保留在 `bot_onebot_config` 和 `bot_qq_official_config`。集群关系通过独立关联表表达，
不把 `cluster_id`、Redis 租约或临时状态塞进协议配置表。

## 4. Redis 职责

多实例部署时 Redis 至少承担：

- 连接租约：同一机器人实例在任一时刻只允许一个应用节点持有正式连接；
- 消息幂等：按平台、机器人、会话和消息 ID 生成键，通过原子写入确保只处理一次；
- 回复决策：记录消息选择的回复实例，重试时保持同一决策；
- 节点心跳：保存节点和机器人连接的短期在线状态；
- 分布式限流：同时约束账号、群聊、命令和集群维度；
- Sa-Token 共享会话：管理端流量由多个节点处理时保持登录状态一致。

PostgreSQL 继续保存集群、成员、策略和审计等长期事实；Redis 只保存带 TTL 的运行状态，不能
成为唯一配置源。

## 5. 消息处理流程

```text
平台事件
  -> 标准化消息键
  -> Redis 幂等占位
  -> 业务插件处理一次
  -> 根据集群策略选择在线回复实例
  -> 原子记录回复决策
  -> 发送并记录结果
  -> 有界故障转移
```

消息键不能只使用消息正文，应优先使用平台消息 ID；没有稳定 ID 时组合平台、机器人、会话、
发送者和时间窗口，并明确误判边界。幂等 TTL 必须覆盖平台重投和应用重试窗口。

## 6. 回复策略

建议按以下顺序实现：

1. `STICKY_PRIMARY`：固定主实例，主实例离线才切换；
2. `CONSISTENT_HASH`：按会话稳定映射账号，避免同一群内回复身份频繁变化；
3. `WEIGHTED`：结合账号健康度、速率配额和近期失败做加权选择；
4. `RANDOM`：仅作为明确业务场景的可选策略，不作为默认值。

发送失败只能进行有限次数切换。每次切换都必须复用同一消息幂等记录，避免原账号实际发送
成功但响应丢失后由另一账号再次回复。

## 7. 正向与反向 WebSocket

正向 WS 下，应用节点先竞争实例租约，获租节点才主动连接 OneBot；失去租约必须关闭连接。
反向 WS 下，入口节点从 `X-Self-ID` 或事件 `self_id` 识别账号，再通过共享租约确认连接归属，
负载均衡层还需提供 WebSocket 粘性或显式连接路由。

两种模式可以共存，但应共享 `BotChannelInstance`、消息幂等和集群选择模型。当前正向 WS 已能
通过 `get_login_info` 主动发现账号，没有必要仅为账号发现切换为反向模式。

## 8. 分阶段实施

1. 增加 `bot_cluster`、成员关联和稳定回复策略，不改变单机行为；
2. 接入 Redis 并先迁移 Sa-Token、节点心跳和消息幂等；
3. 增加连接租约，验证同一实例不会被两个节点同时连接；
4. 实现固定主实例与故障转移，补充重复投递、租约过期和脑裂测试；
5. 再评估一致性哈希、加权选择和反向 WS 动态接入。

上线前必须通过双节点故障演练验证：重复消息只执行一次、租约切换不重复回复、Redis 短暂
不可用时默认停止新处理而不是放行重复处理。
