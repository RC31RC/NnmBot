# 项目架构与开发约定

详细编码规范见 [AGENTS.md](../AGENTS.md)。后端与前端分别在 `NnmBot`、`nnm-admin-web` 仓库，通过 `/api/admin/v1` 协作；本地后端端口 8080，前端端口 3006。

## 模块职责

| 模块 | 职责 |
| --- | --- |
| `nnm-common` | 与业务无关的错误、响应、HTTP、存储及任务基础设施 |
| `nnm-core` | 插件协议、命令执行、实例连接、回复路由、成员和积分等共用机器人能力 |
| `nnm-render` | 图片/HTML 渲染实现 |
| `nnm-warframe` | 官方静态资料、社区维护、论坛、WorldState、仲裁、Market、紫卡与订阅 |
| `nnm-admin` | 登录、RBAC、机器人配置和管理 API |
| `nnm-app` | 应用入口、模块装配及跨模块适配 |

Common 不反向依赖业务模块；Warframe 的 API Controller 由应用装配，与 Admin 通过明确端口协作。已有前端页面、路由和组件继续保留，不能因后端归包删除功能示例。

## Admin 与 Warframe 的共同目录

```text
<module>/src/main/java/com/nnm/bot/<business>/
  constant/                         枚举和稳定常量，按业务细分
  pojo/
    entity/<来源或业务>/            JPA 表实体，保留原名称
    dto/<来源或业务>/               Repository 投影、服务传输、增改输入
    vo/<来源或业务>/                HTTP、命令和模板展示
    query/<来源或业务>/             查询入参
  repository/<来源或业务>/
    XxxRepository.java              CRUD、派生查询、Specification
    custom/XxxRepositoryCustom.java 按需的复杂查询接口
    impl/XxxRepositoryCustomImpl.java
  service/<业务>/XxxService.java     服务接口
  service/<业务>/impl/              实现和私有编排状态
  controller/                      HTTP 协议、参数、权限
  controller/assembler/            DTO 到前端 VO 的转换
  parser/<来源或业务>/              输入和外部协议解析
  mapper/<业务>/                    有复用价值的纯对象映射
  client/                          外部访问
  storage/                         文件和对象存储
  cache/                           JVM 索引和快照缓存
  event/                           Spring 本地事件与订阅
  schedule/                        所有本地和 RDT 定时入口
  mq/
    consumer/<业务>/
    message/<业务>/
    messagedescriptor/<业务>/
    consumerdescriptor/<业务>/
```

目录按实际职责建立，不创建无调用点的空包。`pojo` 只是数据对象的目录，不是 Maven 模块；不保留一个同时塞入实体、传输、显示对象的 `model` 包。内部状态和上游协议对象按实际归属组织，不强行加 DTO/VO 后缀。

Warframe 的实体和 Repository 区分 `official`、`community`、`forum` 等实际来源；官方再按 equipment、upgrade、worldstate 等稳定分区组织。Admin 按 auth、system、bot/channel、command、group、scope、role、notification 等业务归包。表名称和实体名称不因本次归包变化。

## 调用和持久化边界

```text
HTTP / Plugin → Service 接口 → Repository → JPA / Hibernate
                       ↓
                 client / cache / storage
DTO → Controller / Plugin → VO → API / CommandResult / 模板
```

Controller 和 Plugin 只转换协议、参数和展示合同。Service 组合多个 Repository，管理事务、校验、缓存及一致性，不写 SQL、QueryDSL、Q 类或 EntityManager。Repository 是唯一数据访问入口，不包含来源优先级等业务规则。

读取返回非受管 DTO；写入在服务事务中使用实体并显式 `save(...)`。简单查询使用派生方法，常规父子加载用 EntityGraph/fetch join，动态条件优先 Specification。只有多表动态筛选、exists 子查询、复杂聚合或动态关联加载等明确需求才增加 QueryDSL Custom fragment；投影用 `Projections.bean`，不为全部 Repository 配一份空实现。

每个官方 JSON 各自拥有主表和具体 Repository，无跨 JSON 总父表。本 JSON 内必要子表通过 JPA 双向关联维护，数据库关联列不设物理外键；删除、覆盖和替换通过主表统一维护该 JSON 内关系树，调用方不分别删除孙表和子表。

## 命名和数据合同

- Entity 保留原名，不加 DO/Entity 后缀。
- 服务传输和新增/修改输入使用 `DTO`；显示使用 `VO`；查询入参使用 `Query`。嵌套类型同样遵循后缀。
- DTO/VO 只按业务分包，不再增加 `input/output`。增改可复用同一 DTO；具有不同字段的登录凭据和令牌输出使用不同 DTO。
- 超过两个查询参数使用明确 Query；不用裸 Map 替代查询合同。
- 枚举归 `constant`；相关枚举有共同职责和调用方时可用同一常量容器的内部枚举。
- 简单映射直接构造。字段多、重复且确有复用价值时才考虑 MapStruct，不额外创造万能映射器。

本地运行、数据库和验证见 [开发验证与待办](开发验证与待办.md)、[SQL说明](sql/README.md)；数据导入见 [Warframe数据模型与导入](Warframe数据模型与导入.md)。
